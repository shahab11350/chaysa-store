# فاز ۵ چِک — امنیت و کنترل خطا

- تاریخ: 2026-11-20
- وضعیت: پیش‌نویس طراحی برای بازبینی و تأیید مالک
- شاخه: `design/chaysa-control-phase5-security-error-control-2026-11-20`
- دامنه این اقدام: ممیزی read-only کد موجود و طراحی کنترل‌های امنیتی/خطا
- مبنای عملیاتی بررسی‌شده: شاخه `chaysa-backup`

## 1. هدف و محدودیت

هدف این فاز تعریف دفاع چندلایه برای هسته چِک، پنل مالک، داده‌های سفارش، پرداخت، نقش‌ها، API و ارتباطات است؛ همچنین باید خطاها بدون افشای اطلاعات حساس مهار و قابل پیگیری شوند.

این فاز فعلاً طراحی و ممیزی است. هیچ کد، رمز، secret، دسترسی، تنظیم امنیتی، API، زیرساخت، پیام‌رسان یا Production تغییر نمی‌کند. مسیر خرید مشتری تا انتشار نهایی باید بدون تغییر بماند. محیط مستقل CHAYSA CHECK هنوز ایجاد نشده؛ بنابراین آزمون نفوذ یا آزمون اجرایی روی سرویس واقعی انجام نمی‌شود.

## 2. مبنای ممیزی read-only

فایل‌های عملیاتی خوانده‌شده:
- `server.js` — SHA: `d3b50a464a4ad6848c8b68dd0136b8d7a5667405`
- `package.json` — SHA: `10bb2557cf8e767e7fb891939859cc865f9078e4`
- `admin.html` — SHA: `4bccab88fdc38b666b350c87b1e3272e80b0dba1`

مشاهدات مستقیم:
1. سرور Node.js و Express 4.21.2 است؛ وابستگی Multer با نسخه `^1.4.5-lts.1` اعلام شده است.
2. بدنه JSON حداکثر 1MB محدود شده است.
3. احراز هویت پنل با `ADMIN_PASSWORD` و کوکی HMAC دارای `httpOnly`, `secure`, `sameSite=strict` و عمر ۸ ساعت انجام می‌شود. امضای کوکی به secret وابسته و زمان انقضا کنترل می‌شود.
4. محدودسازی ورود و برخی APIها با Map در حافظه همان پردازش پیاده شده؛ وضعیت محدودسازی پس از restart پاک می‌شود و بین replicaها مشترک نیست.
5. `requireAdmin` در صورت وجود Origin، مبدأ را با host/protocol مقایسه می‌کند؛ نبود Origin به‌تنهایی رد نمی‌شود. SameSite=Strict یک لایه کمکی است، نه جایگزین کنترل کامل CSRF.
6. `admin.html` از شمارش بازدید مستثنا است، اما فایل از طریق static hosting عمومی قابل دریافت است. قفل‌بودن APIهای مدیریتی به معنی خصوصی‌بودن خود HTML یا محتوای داخل آن نیست.
7. `express.static(ROOT)` با فهرستی از نام فایل‌های مسدودشده استفاده می‌شود؛ این فهرست باید در طراحی امنیتی با allowlist مسیرهای عمومی و جداسازی فایل‌های حساس جایگزین/تکمیل شود.
8. `trust proxy` روی عدد 1 تنظیم شده؛ در استقرار باید تعداد و زنجیره واقعی proxyها مشخص و spoof نشدن IP/پروتکل آزموده شود، زیرا rate limit و secure-cookie به این داده‌ها وابسته‌اند.
9. آپلودهای Multer سقف حجم و تعداد فایل دارند و برخی مسیرها بررسی محتوای فایل انجام می‌دهند؛ برای هر مسیر باید تشخیص نوع واقعی محتوا، نام‌گذاری امن، مسیر خارج از public root و کنترل دسترسی دانلود یکسان و صریح باشد.
10. خطای نهایی Express پیام عمومی برمی‌گرداند؛ در کد مسیرهای متعددی catch وجود دارد. سیاست ثبت ساختاریافته خطا، شناسه هم‌بستگی و تفکیک خطای قابل نمایش از جزئیات داخلی باید یکپارچه شود.
11. وضعیت فعلی وابستگی‌ها و نسخه‌های امن باید در زمان اجرای فاز با lockfile و منابع رسمی بررسی شود؛ از نسخه package range به‌تنهایی نمی‌توان نسخه دقیق نصب‌شده یا وجود/عدم وجود آسیب‌پذیری را نتیجه گرفت.

هیچ تلاش ورود ناموفق، ارسال فرم، آپلود، سفارش، پرداخت، تغییر وضعیت یا آزمون امنیتی روی Production انجام نشد.

## 3. طبقه‌بندی یافته‌های قابل پیگیری

| شناسه | مشاهده | اهمیت طراحی | کنترل موردنیاز |
|---|---|---|---|
| SEC-01 | HTML پنل از static root قابل دریافت است | بالا برای محرمانگی رابط/اطلاعات تعبیه‌شده | انتقال داشبورد خصوصی به مسیر احراز هویت‌شده یا حذف هر داده/جزئیات حساس از HTML عمومی؛ API همچنان مستقل محافظت شود |
| SEC-02 | Rate limit فقط در حافظه پردازش است | بالا برای مقاومت در برابر brute force و چند replica | محدودکننده مشترک/پایدار یا راهکار edge رایگان و قابل اثبات؛ سقف و پنجره برای هر مسیر حساس |
| SEC-03 | کنترل Origin فقط در صورت وجود header انجام می‌شود | متوسط/بالا برای درخواست‌های تغییردهنده | CSRF token یا الگوی معتبر ضد-CSRF به‌علاوه Origin/Referer policy و SameSite؛ رد مبدأ نامعتبر و سیاست روشن برای کلاینت فاقد Origin |
| SEC-04 | توکن پنل stateless و تا پایان ۸ ساعت قابل اعتبارسنجی است | متوسط برای لغو نشست | شناسه نشست قابل ابطال، چرخش کلید/رمز، خروج مؤثر و پایان نشست؛ یا ثبت نسخه نشست/زمان ابطال |
| SEC-05 | Static serving بر denylist نام فایل تکیه دارد | بالا برای جلوگیری از انتشار تصادفی اسناد و فایل‌ها | public allowlist، خارج‌کردن اسناد، سورس، پشتیبان‌ها و فایل‌های داده از web root |
| SEC-06 | وابستگی Multer روی شاخه قدیمی 1.x range است | نیازمند بررسی فوری نسخه/مشاوره امنیتی | inventory دقیق lockfile، بررسی advisory رسمی و ارتقا کنترل‌شده پس از آزمون سازگاری |
| SEC-07 | سیاست یکپارچه آپلود برای همه مسیرها اثبات نشده | متوسط/بالا بسته به نوع فایل | بررسی magic bytes، MIME واقعی، پسوند تولیدشده توسط سرور، سقف حجم/تعداد، اسکن در صورت امکان رایگان، عدم اجرای فایل و دانلود احراز هویت‌شده |
| SEC-08 | لاگ ساختاریافته و correlation ID در همه مسیرها اثبات نشده | متوسط برای کشف/رسیدگی | شناسه درخواست، ثبت actor/action/result، حذف PII و secret از لاگ، هشدار برای رویدادهای حساس |
| SEC-09 | زنجیره proxy و اعتماد به IP نیازمند تطبیق با محیط واقعی است | متوسط | تعیین proxyهای trusted و آزمون جعل X-Forwarded-For؛ اتکا به IP تنها عامل احراز هویت نباشد |
| SEC-10 | پنل مالک و پنل‌های نقش‌محور در مدل فعلی باید تفکیک شوند | بالا | deny-by-default، مجوز سمت سرور برای هر endpoint و هر رکورد، آزمون دسترسی افقی/عمودی |

این جدول فهرست طراحی و پیگیری است؛ شدت نهایی هر مورد با threat modeling و آزمون ایزوله تعیین می‌شود. موارد بالا به‌تنهایی اثبات سوءاستفاده یا رخداد نفوذ نیستند.

## 4. مدل تهدید و دارایی‌های محافظت‌شونده

دارایی‌ها:
- اطلاعات هویتی، تماس، نشانی و سوابق سفارش مشتری.
- مبالغ، بررسی پرداخت، تصمیم مالک و مجوز آماده‌سازی.
- شناسه‌های سفارش و کدهای رهگیری.
- secrets، رمز مدیر، کلید امضای نشست و توکن ربات‌ها.
- داده‌های موجودی، قیمت و تنظیمات مدیریتی.
- فایل‌های بارگذاری‌شده و اسناد داخلی.
- رویدادهای حسابرسی و نسخه‌های پشتیبان.

تهدیدها:
- حدس رمز و تصاحب حساب.
- جعل درخواست و CSRF.
- دسترسی غیرمجاز به endpoint یا رکورد دیگر.
- افشای فایل از مسیر static یا upload.
- تزریق داده نامعتبر، payload بزرگ یا فایل مخرب.
- تکرار درخواست، race condition و تغییر وضعیت خارج از توالی.
- افشای secret در پاسخ، log، خطای stack یا فایل عمومی.
- ارسال اعلان به گیرنده اشتباه یا عبور پیام آزمایشی به کانال واقعی.
- خرابی فایل/داده، پرشدن دیسک، قطع شبکه و retry تکراری.
- سوءاستفاده داخلی یا دسترسی بیش از حد نقش‌ها.

## 5. کنترل‌های امنیتی هدف

### 5.1 هویت و نشست
- احراز هویت مالک با رمز قوی و ذخیره secret فقط در secret manager/environment امن؛ هرگز در مخزن، HTML، log یا فایل قابل دانلود.
- بررسی امکان استفاده از hash مقاوم رمز (Argon2id/bcrypt/scrypt) با salt و پارامترهای به‌روز؛ انتخاب کتابخانه پس از بررسی پشتیبانی Node و هزینه صفر.
- نشست تصادفی و قابل ابطال، عمر محدود، چرخش پس از ورود، logout واقعی، کوکی Secure/HttpOnly/SameSite و عدم ذخیره token در localStorage.
- MFA برای مالک در صورت وجود راهکار رایگان و قابل نگهداری؛ تا آن زمان محدودسازی شدید و هشدار ورود.
- خطای ورود عمومی و بدون مشخص‌کردن اینکه نام کاربری یا رمز کدام اشتباه است.

### 5.2 مجوز و جداسازی نقش
- پیش‌فرض deny؛ هر endpoint خصوصی باید middleware احراز هویت و مجوز داشته باشد.
- مجوز سمت سرور و در سطح عملیات و رکورد بررسی شود؛ مخفی‌کردن دکمه در UI کنترل امنیتی نیست.
- مالک تنها تصمیم‌گیر نهایی پرداخت، لغو و بازپرداخت مطابق مصوبه فاز ۳ است.
- ربات پیام‌رسان هیچ فرمان حساس یا تغییر وضعیت اجرایی ندارد.
- داده مشتری فقط در حد نیاز و فقط برای سفارش تخصیص‌یافته نمایش داده شود.
- آزمون‌های منفی برای دسترسی ناشناس، نقش اشتباه، شناسه سفارش متعلق به دیگران و تغییر مستقیم API.

### 5.3 حفاظت API و وب
- CSRF token برای درخواست‌های مبتنی بر cookie، بررسی Origin/Referer با سیاست صریح، SameSite و رد درخواست cross-origin نامعتبر.
- CORS فقط در صورت نیاز و با allowlist دقیق؛ wildcard همراه credential ممنوع.
- محدودیت اندازه body، تعداد درخواست، طول رشته، نوع داده و schema validation برای همه ورودی‌ها.
- پارامترسازی SQL در صورت استفاده از DB؛ عدم ساخت query با الحاق ورودی.
- Content Security Policy، HSTS در لایه‌ای که TLS را خاتمه می‌دهد، X-Content-Type-Options، Referrer-Policy و frame-ancestors؛ ابتدا وضعیت headerهای Railway/CDN بررسی شود تا سیاست تکراری/متناقض ایجاد نشود.
- پاسخ‌های خصوصی no-store؛ عدم cache شدن داده سفارش/مشتری.
- کنترل method و content-type؛ مسیرهای عمومی و مدیریتی کاملاً تفکیک شوند.

### 5.4 فایل و آپلود
- فایل‌ها خارج از web root نگهداری شوند؛ نام تصادفی سمت سرور، عدم اعتماد به نام/پسوند/MIME ارسالی.
- بررسی magic bytes و محدودیت واقعی فرمت/حجم/تعداد؛ رد فایل ناسازگار.
- دانلود فقط با مجوز رکورد و مسیر canonical؛ جلوگیری از path traversal.
- فایل آپلودی هرگز به‌عنوان HTML/JavaScript اجرا یا inline نمایش داده نشود.
- پاک‌سازی و نگهداری فایل‌ها تابع سیاست مصوب داده مشتری باشد؛ تا تصویب سیاست حذف خودکار فعال نشود.

### 5.5 اسرار و ارتباطات
- secretهای Production و Simulation مجزا و غیرقابل جایگزینی با یکدیگر.
- عدم چاپ token، رمز، شناسه کامل مشتری یا payload حساس در log.
- مقصد پیام آزمایشی ثابت و allowlist‌شده؛ fail-closed در صورت نامشخص بودن محیط یا مقصد.
- کلیدهای webhook تصادفی، قابل چرخش و مستقل از secretهای دیگر؛ اعتبارسنجی امضای/secret ارائه‌دهنده در هر webhook.
- timeout، retry محدود و idempotency برای ارتباطات بیرونی؛ پیام‌های حساس از outbox و پس از commit.
- در خطای شبکه، هیچ عملیات مالی/سفارشی به‌صورت حدسی موفق اعلام نشود.

## 6. کنترل خطا و تاب‌آوری

1. خطاهای ورودی 400، عدم احراز هویت 401، عدم مجوز 403، تعارض وضعیت 409، محدودیت 429 و خطای داخلی 500 با پاسخ‌های ثابت و بدون جزئیات داخلی.
2. پاسخ عمومی هرگز stack trace، مسیر فایل، query، secret یا داده مشتری را برنگرداند.
3. هر درخواست شناسه هم‌بستگی داشته باشد؛ همان شناسه در پاسخ و log امن ثبت شود.
4. log ساختاریافته شامل زمان UTC، request ID، actor ID/role، action، resource ID، نتیجه و کد خطا باشد؛ PII و credential ثبت نشود.
5. خطای قابل retry از خطای دائمی تفکیک شود؛ retry محدود با backoff و سقف تلاش.
6. برای عملیات مالی/وضعیت سفارش، شکست یا timeout به وضعیت مبهم و نیازمند بررسی منتهی شود، نه موفقیت فرضی.
7. عملیات چندمرحله‌ای با تراکنش DB و outbox انجام شود؛ از write هم‌زمان ناسازگار و overwrite فایل جلوگیری شود.
8. health endpoint فقط وضعیت حداقلی سرویس را افشا کند؛ جزئیات زیرساخت/نسخه/secret عمومی نشود.
9. در صورت کمبود فضای ذخیره‌سازی، خرابی DB یا شکست backup، عملیات تغییردهنده متوقف و هشدار مدیریتی ثبت شود؛ سفارش تأییدنشده یا مجوز آماده‌سازی ساخته نشود.
10. graceful shutdown و بستن اتصال‌ها/توقف workerها طراحی و آزموده شود.

## 7. مدیریت رخداد و بازیابی

- طبقه‌بندی رخداد: افشای داده، تصاحب حساب، دسترسی غیرمجاز، پیام اشتباه، خرابی داده، از دست‌رفتن secret و اختلال سرویس.
- گام‌ها: مهار دسترسی/کلید، حفظ شواهد، تعیین دامنه، اطلاع به مالک، بازیابی از نسخه سالم، بازبینی و ثبت علت ریشه‌ای.
- چرخش secret فقط با طرح هماهنگ و تأیید مالک؛ هرگز در متن گزارش secret واقعی درج نشود.
- backup رمزگذاری‌شده و restore آزمایشی مطابق اهداف فاز ۴ (RPO ≤ 24h و RTO ≤ 8h)؛ این اهداف تا آزمون واقعی تضمین‌شده نیستند.
- پس از رخداد، دسترسی و لاگ‌ها بازبینی و اصلاحات در شاخه جداگانه آزمون می‌شوند.

## 8. برنامه آزمون پذیرش امنیتی — فقط محیط Simulation

- احراز هویت: رمز اشتباه، brute-force، انقضای نشست، logout و ابطال نشست.
- مجوز: نقش ناشناس/غلط، دسترسی افقی به سفارش دیگر، دسترسی عمودی به عملیات مالک.
- CSRF/CORS: Origin غایب/نامعتبر، درخواست cross-origin و token نامعتبر.
- ورودی: JSON بزرگ، فیلد اضافی، نوع داده غلط، رشته طولانی، Unicode و payload خراب.
- آپلود: فایل واقعی/جعلی، MIME جعلی، پسوند دوگانه، فایل بیش‌ازحد، path traversal و دانلود بدون مجوز.
- نرخ: عبور از سقف در یک پردازش، restart و چند replica؛ اثبات شود کنترل در مقیاس محیط واقعاً کار می‌کند.
- خطا: قطع DB، دیسک پر، timeout تلگرام/روبیکا، پاسخ ناقص، retry و shutdown.
- جداسازی: هر درخواست/پیام Simulation فقط به داده و sink آزمایشی برسد؛ هیچ مسیر شبکه‌ای به secrets یا گیرنده Production وجود نداشته باشد.
- حسابرسی: هر اقدام حساس actor، زمان، نتیجه و request ID داشته باشد و امکان دستکاری/حذف عادی رویدادها نباشد.
- آزمون نفوذ فقط با محدوده و مجوز مشخص روی محیط خصوصی؛ هرگز روی سایت عملیاتی یا مشتریان واقعی.

## 9. معیارهای پذیرش فاز ۵

- ماتریس تهدید و کنترل برای هر دارایی و نقش کامل باشد.
- تمام endpointها طبقه‌بندی عمومی/خصوصی و مجوز لازم داشته باشند.
- نشست قابل ابطال، ضد-CSRF، rate limit قابل اتکا و مدیریت secret طراحی و در Simulation آزموده شوند.
- فایل‌های حساس از static root خارج و آپلود/دانلود امن شود.
- خطاها قابل پیگیری و بدون افشای اطلاعات باشند.
- آزمون‌های منفی و رخدادهای امنیتی ثبت شوند.
- مسیر Simulation از Production و گیرندگان واقعی ایزوله بماند.
- هیچ تغییری برای مشتری تا انتشار نهایی قابل مشاهده یا احساس نباشد.
- مالک طراحی و نتایج آزمون را جداگانه تأیید کند.

## 10. تصمیم‌های باز برای مالک

1. **ورود دومرحله‌ای مالک:** آیا MFA رایگان را به‌عنوان الزام ورود مالک تصویب می‌کنید؟ پیشنهاد: بله، در صورت پشتیبانی قابل اتکا؛ در غیر این صورت، نشست محدود، رمز قوی و هشدار ورود تا فراهم‌شدن MFA.
2. **نشست مالک:** پیشنهاد عمر نشست ۳۰ دقیقه عدم فعالیت و حداکثر ۸ ساعت از زمان ورود، با ابطال هنگام خروج و تغییر رمز. آیا تصویب می‌کنید؟
3. **اعلان امنیتی:** آیا ورود موفق/ناموفق غیرعادی، قفل نرخ، تغییر نقش و عملیات حساس به مالک از کانال خصوصی و مستقل اعلان شود؟ پیشنهاد: بله، بدون درج اطلاعات مشتری یا secret در پیام.
4. **ثبت رخداد امنیتی:** پیشنهاد نگهداری رخدادهای امنیتی حداقل ۱۸۰ روز، با دسترسی محدود و بدون PII غیرضروری. مدت نگهداری اطلاعات سفارش/مشتری از این سیاست جداست و همچنان تصمیم باز فاز ۴ باقی می‌ماند.

## 11. وضعیت و مرز اجرا

- فاز ۵ در وضعیت پیش‌نویس طراحی و ممیزی read-only است.
- فقط فایل‌های شاخه عملیاتی خوانده شدند؛ هیچ درخواست تغییردهنده یا آزمون عملیاتی اجرا نشد.
- هیچ secret یا رمز خوانده، چاپ، کپی یا تغییر داده نشد.
- هیچ کد، dependency، حساب، نشست، دسترسی، webhook، API، تنظیم Railway یا Production تغییر نکرد.
- محیط مستقل CHAYSA CHECK هنوز ساخته نشده؛ آزمون‌های امنیتی اجرایی تا آماده‌شدن محیط ایزوله انجام نمی‌شوند.
- مشتری تا انتشار نهایی نباید هیچ تغییری در مسیر خرید یا تجربه سایت مشاهده/احساس کند.
- این سند پیشنهاد طراحی است؛ تأیید مالک، اجرا و آزمون هر کدام مراحل مستقل‌اند.
